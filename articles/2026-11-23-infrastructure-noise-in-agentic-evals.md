# Quantifying infrastructure noise in agentic coding evals
- 日期：2026-11-23
- 链接：https://www.anthropic.com/research/infrastructure-noise
- 分类：engineering（AI 评测/基础设施）
- 作者：Gian Segato（Anthropic，感谢 Nicholas Carlini、Jeremy Hadfield、Mike Merrill、Alex Shaw）

## 讲了什么

SWE-bench、Terminal-Bench 这类 agentic coding 基准常被用来比较前沿模型的软件工程能力，榜首之间往往只差几个百分点，而这些分数常被当成精确的能力测量。Anthropic 在内部实验中发现：仅基础设施配置一项，就能造出超过这个差距的分数差。Terminal-Bench 2.0 上，资源最充足和最受限的两种配置相差 6 个百分点（p < 0.01）。

起因是他们用 GKE 跑 Terminal-Bench 2.0 时分数对不上官方榜，排查发现 6% 的任务因 pod 错误失败。根因是资源强制执行方式：容器运行时用两个参数管资源——保证分配（guaranteed allocation）和硬上限（超过即杀）。他们的实现把两者设成同一个值，零余量，一次瞬态内存尖峰就能 OOM 杀掉本来能通过的容器。

于是做了对照实验：同一个模型、同一个 harness、同一批任务，只改资源配置，从 1x（严格等于推荐值）到完全不限，共六档。结果分两段：1x 到 3x，基础设施错误率从 5.8% 降到 2.1%，但成功率在噪声范围内波动（p=0.40）——这段多给的资源只是在修可靠性问题；3x 之后，成功率上升快于错误率下降，因为额外资源让 agent 能采用"只有资源宽裕才行得通"的策略，比如装大型依赖、跑内存重的测试套件。完全不限时比 1x 高出 6 个百分点。

最生动的例子是 `bn-fit-modify`（贝叶斯网络拟合）：一些模型的第一反应是装 pandas、networkx、scikit-learn 全家桶。资源宽裕时装得完，资源紧张时 pod 在安装阶段就 OOM，一行解题代码都没写。也存在更省的策略（只用标准库手搓数学），但不同模型默认策略不同，资源配置决定了哪种策略恰好能活下来。SWE-bench 上复现：RAM 拉到 5 倍，227 题 × 10 样本，分数单调上升 1.54 个百分点——幅度小但方向一致。

其他变量同样在污染测量：时间上限、并发度、出口带宽，甚至一天中的时刻（API 延迟随流量波动）。文章建议：每个任务同时指定 guarantee 和 kill 阈值两个参数而不是单个定值，两者之间的带宽校准到"下限分数和上限分数落在噪声之内"（Terminal-Bench 2.0 上 3x 上限是合理折中）；多时点、多日重复跑平均掉噪声；资源配置应像 prompt 格式、采样温度一样被当作一等实验变量记录。结论：在资源配置标准化之前，小于 3 个百分点的榜单差距值得怀疑——几个点的领先可能真是能力差，也可能只是一台更大的虚拟机。

## 关键洞察

1. **Agentic 评测本质是端到端系统测试，不是模型测试**。静态 benchmark 里运行时是个被动容器，agent 评测里运行时本身就是解题过程的一部分：装依赖、跑测试、迭代多轮都发生在环境里。"两个资源预算不同的 agent 不是在考同一张卷子"——这句话把测量对象从"模型"悄悄换成了"模型+环境"复合系统。
2. **3x 附近存在一个相变点：资源先是噪声，然后变成测量变量本身**。低于 3x，多给资源只修掉瞬态尖峰导致的假失败（修可靠性）；高于 3x，资源开始改变 agent 可用的策略空间（改信号）。这意味着"基础设施噪声"和"真实能力差异"不是两个独立量，而是同一个变量在不同区间的两种表现。理解这一点比记住 6 个百分点这个数字更有用。
3. **资源限制是一份隐性的测试规格**。紧限制奖励"写得又省又快"的模型，宽限制奖励"会充分利用资源"的模型，两者都是合法测量，但混在一个分数里就失去可解释性。测量条件定义测量对象，这跟物理实验里"仪器精度决定你能看到什么尺度"是同一类问题。
4. **保证分配和硬上限之间必须有头寸（headroom）**。把两者设成同一个值，等于把正常的瞬态波动直接判死。任何"预算恰好等于需求"的系统设计都有这个问题，agent 评测只是把它暴露了。

## 落到你手上

1. **本地模型对比前先排除"资源假象"**：你在 .114 上跑 Qwen3.5-27B，如果之后想对比 27B 和小模型（或新旧版本）在同一批任务上的表现，先固定环境——同一台机、同样的内存上限、单任务串行，并记录 OOM/超时次数。27B 显存和内存占用更大，如果给两个模型同样的资源限制，大模型可能只是"装不动依赖、跑不动测试"而显得更笨。给 3 倍余量再比一次，两次结果差超过 3 个百分点就说明资源在污染结论。
2. **自建推理服务的资源规划用"双参数"思路**：EPYC 7452 上同时跑推理服务和别的任务时，别把内存/显存限制卡死在基准需求上。按文章原则：保底分配留够，硬上限单独设（参考 2-3 倍），并验证两种配置下的吞吐/成功率落在噪声内，再收紧。随机 OOM 和"高峰期变慢"多半是零余量导致的，不是硬件不够。
3. **给 HanaAgent 建模型 A/B 时直接抄文章的方法论**：将来在 chenliangorient.xyz 上对比本地 Qwen 和云端模型时，不要跑一次下结论。按它推荐的三个动作：固定 per-task 资源并记录配置、跨多个时段（避开 API 高峰）、多日重复取平均。一天内一次通过/失败不构成证据。
