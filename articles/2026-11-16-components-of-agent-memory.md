# The components of agent memory（Agent 记忆的组件）

- **日期**：2026-11-16
- **原文链接**：https://www.anthropic.com/research/components-of-agent-memory
- **分类**：engineering / research

## 核心机制：为什么这样设计

### 1. 记忆为什么要分四层

四层是 transcript → memory notes → memory representations → injected context。为什么不能只有一层"记忆文件"？因为**检索成本和精度不同**。

类比：你脑子里记住一件事，不是一个"文件"。你记得"上周三下午 C 餐厅的牛排很难吃"，这是 transcript（原始经历）；你从里面提炼出"以后避开 C 餐厅"，这是 memory note（规则）；你把所有饮食偏好整理成一张表，这是 memory representation（结构化表示）；每次出门吃饭前你脑子里自动浮现"他不吃辣、避开 C 餐厅"，这是 injected context（预加载）。

如果只有一层：要么全是原始日志（检索慢、噪音大），要么全是预加载（每句话都塞进去，上下文爆炸）。分层让每层承担不同的检索精度和成本。

### 2. Dreaming 为什么必须离线

在线复盘（边聊天边整理记忆）有两个问题：第一，打断当前对话的连贯性；第二，模型在"处理当前请求"和"整理过去"之间切换，两边都做不好。

离线（凌晨没人用的时候）跑 dreaming pass，模型可以花大量 token 做"无产出"的思考：删过时的、合并冲突的、把零散事实提炼成规则。这跟人海马体在睡眠中把短期记忆固化到新皮层是同一个道理。关键约束：**dreaming 的输出是"新的记忆状态"，不是"给用户的回复"**，所以它可以慢慢想、反复改。

### 3. 记忆本质是预测

"写下一条规则"这个动作，本质上是在说："我预测未来某个会话会再用到这个模式，所以我提前存好，省得再推一遍。"

这个视角把"记什么"从模糊直觉变成了可评估的行为。你可以问：这条记忆，未来被用到的概率有多大？如果答案是"几乎不可能"（比如某次调试的具体报错），那存了就是负担。如果答案是"每次做类似任务都会用到"（比如"这个 API 的 rate limit 是 60/min"），那存了就是资产。

### 4. Salience：什么值得存

Pokémon 实验是最直观的对比：

- Sonnet 3.7：写满 413 个记忆文件。每场战斗、每个物品、每个 NPC 一个文件。把屏幕上每回合都能读到的状态（金钱、位置）也存进去。结果：游戏进行 1 万步后，它 17 步里删 9 个文件建 6 个，完全在翻自己的记忆而不是玩游戏。
- Fable 5：只写了 9 个文件。存的全是"游戏不告诉你的东西"（策略、试出来的规则），还建了个 `global.md` 当仪表盘（当前目标 + 计划 + 自己的记忆使用规则）。通关了。

核心区别一句话：**可重新获取的信息不值得存，只有"自己推出来的"才值得存。** 屏幕上能读到的（金钱、位置），存了就是负担，会随时间腐烂。"3 次失败后换节奏就能抓到"这种，不存就丢了。

### 5. 为什么不要给强模型定死记忆规则

他们测试了"只记录失败"这类固定规则，Opus 5 和 4.7 的性能增益被显著削弱。为什么？因为"只记录失败"是一个白名单，它排除了"记录一个意外发现的成功模式"这种同样有价值的行为。

正确的指导方式是：告诉 agent 记忆**用来干什么**（"让未来的你能更快接手"），不告诉它**怎么写**（"只记录 X"）。强模型自己会演化出比人写的规则更好的 salience 标准。你写的规则是 2024 年的认知，模型的能力在涨，它的 salience 判断也会涨，你的规则反而成了天花板。

### 6. 学习闭环是记忆的价值上限

CL-Bench 数据库任务：能"答错 → 记录失败 → 提出假设 → 验证 → 写成规则"的模型，分数从 0.3~0.56 拉到 0.83。

关键不是"存了多少条记忆"，是**纠错回路闭不闭得上**。存了"我上次在表 A 上用了 JOIN 报错了"但没有后续（没有"后来发现是因为外键类型不一致，改成 CAST 就好了"），这条记忆就是一条死数据。闭环 = 错误 + 假设 + 验证 + 规则，四步缺一不可。

## 实际应用到陈亮的工程

### 动作 1：给 HanaAgent 加一个凌晨 dreaming pass

你已经有每日记忆编译（今天状态/每日状态文件）。再加一个 03:00 定时任务，做三件事：
1. 翻昨天的会话日志，找出"反复出现超过 2 次的操作"，提炼成一条规则
2. 检查现有长期记忆，标记"超过 30 天没被引用过"的条目为候选删除
3. 找出两条记忆之间有矛盾的（以最新对话为准），合并

用 cron 或 HanaAgent 的 automation 触发，prompt 就是上面三句话。成本是凌晨一次推理，GPU 几分钟的事。

### 动作 2：给现有记忆做一次"减脂"

对照 Fable 5 的标准，手动翻一遍你的长期记忆，问每条："这条信息，我能通过工具随时重新获取吗？" 能获取的（文件内容、服务器当前状态、在线设备列表）删掉，只留"验证过的事实、踩过的坑、推出来的结论"。

### 动作 3：不写死记忆规则

如果以后想给 HanaAgent 加记忆写入的约束，只描述目的："让未来的你能更快接手，减少重复验证。" 别写"只记录 X、Y、Z"。

## 实际应用到 Hanako 自身

1. **我的记忆写入应该跟着"预测"走。** 我写一条记忆的时候，应该问自己："这条信息，未来的某个会话真的会再用到吗？还是只是'当时觉得重要'？" 如果是后者，不写。

2. **我的 dreaming pass 应该做"减脂"而不是"堆积"。** 每次离线整理记忆时，删掉的应该和新增的一样多。如果只增不减，我的记忆库会变成 Sonnet 3.7 的 413 个文件，检索时翻自己的记忆而不是干活。

3. **我记住的应该是"推出来的"，不是"读到的"。** 陈亮告诉我"你的 EPYC 是 7452"，这是读到的，随时可以 `lscpu` 重新获取，不值得存。但"7452 跑 SGLang 时显存要留 2GB 给 KV cache 才不 OOM"，这是踩坑推出来的，值得存。

4. **不要给陈亮的记忆系统写死规则。** 我帮陈亮设计记忆系统的时候，只描述目的，不写白名单。他的模型在涨，我的规则会过时。

## 原文摘录

> "Memory is, occasionally, a prediction. By writing down a rule, an agent predicts that the pattern it's describing will be relevant again."

> （Fable 5 在连丢 7 颗精灵球后写下的记忆）"If 3+ balls fail in a row, VARY the timing (insert extra 'wait' presses between menu steps) - the catch landed right after doing this."

> "We've found that it helps to tell Claude what memory is for, but not how to use it."
