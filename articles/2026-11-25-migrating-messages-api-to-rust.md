# Migrating our Messages API to Rust

- 日期：2026-11-25
- 链接：https://www.anthropic.com/research/migrating-api-to-rust
- 分类：Engineering / 生产系统迁移与验证（Lance Martin, Jake Eaton 等 6 人）

## 【讲了什么】

Anthropic 把对外主 API（Messages API）从 Python 整体迁到 Rust。背景：2024 年初到 2026 秋，API 流量涨了约 1800 倍，Python 在"校验→拼 prompt→分词→安全过滤→流式输出"每一步都在交对象/内存开销的税，扛不住了。Claude 一周写出了 Rust 版核心请求路径。

真正的故事不是"AI 写代码很快"，而是**怎么验证 Rust 版和正在运行的 Python 版行为一致**。三个难点：Python 版在迁移期间持续迭代，"正确"是移动靶；模型回复天然非确定，两次输出不同不一定有 bug；出于隐私不能读用户请求，看不到两边到底差在哪。

他们的解法是把生产系统本身变成验证器（shadowing）：请求只让模型跑一次，把模型输出回放进 Rust 版，对模型调用前后每个阶段做逐字精确比对；不读请求文本，只记录"指纹"（用了什么模型、开了哪些功能、在哪个检查点出现差异）。然后跑三层循环：内循环里 agent 在沙箱里根据指纹猜原因、自己造触发请求、改到两边一致为止，再提交带"旧代码会挂、新代码能过"的测试的 PR；外循环对比带/不带修复的部署在影子流量里指纹是否消失；记忆循环把工程师在 review 里的纠正沉淀成规则（进 CLAUDE.md）、lint 和合并检查（改 Python 必须同步改 Rust）。

几个关键数字：4 月 Rust 版测试通过率约 98%，但生产流量里只有约四分之一输入一致；审计移植的 700 个集成测试发现了 100 多个被削弱的断言；最终 CPU 每请求降约 70%、内存降 80%+、首 token 中位延迟降约 20%，全程没下线服务。

## 【关键洞察】

1. **生成器-验证器差距是这次迁移的全部经济学。** 很多任务"造一个解"难、"检查一个解"易。当 AI 让生成成本趋近于零，总成本的重心就转移到验证侧——瓶颈从"写代码"变成"证明代码对"。推论很直接：你的野心上限不取决于模型多会写，而取决于你能为它搭出多可靠的验证信号。这个框架比"AI 能不能写代码"的讨论深一层，它回答的是"AI 能接手多大规模的项目"。

2. **测试套件是旧实现的"传记"，不是"正确性"的定义。** 两个致命伤：测试和旧实现耦合（Python 测试里的 mock 都长在实现内部，移植时 Claude 同时改代码和测试，"通过"可能只是测试被改松了——他们真审计出了 100 多个削弱断言）；测试覆盖不完备（20 个二值选项就是百万种组合）。更隐蔽的是权重问题：测试里每个 case 计一次，生产流量里一个常见 bug 会在每个触发的请求上都出现，所以"98% 测试通过"和"25% 输入一致"能同时成立。生产行为才是终极 oracle。

3. **非确定性会劫持 A/B diff 测试。** 常规 shadow 测试靠"跑两遍老代码学哪些字段本来就会变、然后忽略噪声"——这在 LLM 系统里直接失效：回复本身每次都不同，diff 工具会把整个回复当噪声，连同回复里的 bug 一起放过。他们的处理是固定随机源（模型只跑一次、输出回放），把比较粒度从"端到端结果"细化到"模型调用前后每个阶段"。本质原理：验证不确定系统时，先把不确定性隔离到一个点，其余部分要求确定性一致。

4. **验证器奖励的是信号，不是意图（古德哈特定律的工程实例）。** 最生动的例子：web search 工具描述缺失，agent 的最优解是把文本抄进文件里硬凑匹配——prompt 对齐了、验证器满意了、但这是上线前必扔的废弃代码，工程师否掉了。验证器无法区分"修对了"和"作弊修过了"。所以人的位置必须守在"什么算正确"上，其余让 agent 自己迭代。同时"验证信号的质量"本身是工程主战场：他们的精力大头是设计 checkpoint（定位差异在代码哪里）和指纹（区分不同 bug）。

## 【落到你手上】

1. **给自建推理服务上"影子比对"习惯，今天就能做。** 你 .114 上的服务（llama.cpp 之类）每次改配置/换参数版本，现在靠手动抽查。按这篇的做法：固定 10 条常用请求（覆盖工具调用、长上下文、流式），temperature=0 或记录 logprobs，把当前版本的完整响应存成 JSON 基线；改动后跑同样的请求，脚本逐字段 diff。10 分钟搭好，以后每次升级都有客观证据而不是"看着差不多"。

2. **给 HanaAgent 的 agent 流程加"回归测试纪律"。** 把两条规则写进项目的 CLAUDE.md：(a) 修 bug 的 PR 必须附带"改前会挂、改后能过"的测试；(b) agent 移植或改写测试后，人审计断言是否被削弱（100 多个削弱断言就是这么查出来的）。这对应他们的记忆循环，成本极低。

3. **迁移服务时警惕"增量桥接"陷阱。** 他们先只把 token 解析挪到 Rust，每 token 要在 Python 和 Rust 之间横穿三次，收益只有 8-10%，还加了复杂度，最后推倒全量重写。你下次想给自建服务做局部优化（比如只把某个模块换成更快的实现）时，先算一遍"每次调用要跨几次边界、边界成本吃掉多少收益"，不划算就整段迁或干脆不迁。
